```python
PROFILES = {
    "Stable":   {"loss": (0.0, 0.8),  "delay": (5, 25),    "jitter": (0, 4),   "duration": (18, 24)},
    "Unstable": {"loss": (3.0, 7.0),  "delay": (40, 120),  "jitter": (8, 25),  "duration": (22, 30)},

}
STATE_WEIGHTS = {"Stable": 0.33, "Unstable": 0.34, "Critical": 0.33}
DURATION_SECONDS = 10800   # 3 hours
```

**Important known issue:** Critical generates more rows/sec than Stable due to packet buffering under high delay (packets accumulate and flush in bursts). This is a receiver artifact — NOT fixed in data, compensated by `class_weight="balanced"` in models.

## Model Development — Full Progression

### Stage 0: Baseline
- Rule-based: loss>8% → Critical, loss>3% → Unstable, else Stable
- Macro F1: **0.455** — Unstable F1=0.00 (loss alone can't detect it)

### Stage 1: Three Models Compared
All used `class_weight="balanced"`, 5-fold TimeSeriesSplit CV, 80/20 time split.

| Model | CV F1 ± std | Held-out F1 | Critical Recall |
|-------|-------------|-------------|-----------------|
| RandomForest | 0.767 ± 0.043 | 0.807 | 0.75 |
| LightGBM | 0.752 ± 0.047 | 0.821 | 0.78 |
| XGBoost (default) | 0.757 ± 0.045 | 0.830 | 0.81 |

XGBoost selected — best held-out F1, best Critical recall, best Critical→Stable error count (408 vs 631 for RF).

### Stage 2: XGBoost Hyperparameter Tuning
40-iteration RandomizedSearchCV, ~28 min runtime.

**Best params found:**
```python
XGBClassifier(
    n_estimators=500,
    max_depth=5,           # shallower than default 6
    learning_rate=0.01,    # much slower than default 0.05
    subsample=0.6,         # more aggressive than default 0.8
    colsample_bytree=0.6,  # more aggressive than default 0.8
    min_child_weight=3,
    gamma=0.2,
    reg_alpha=0.1,         # L1 regularisation
    reg_lambda=1.5,        # L2 regularisation
    use_label_encoder=False,
    eval_metric="mlogloss",
    random_state=42, n_jobs=-1
)
```

**Results:**

## Key Decisions Made

| Decision | What was tried | What was chosen | Why |
|----------|---------------|-----------------|-----|
| Class imbalance | Random undersampling, contiguous block sampling | `class_weight="balanced"` | Preserves time continuity, no data loss |
| Run duration | 60s (too short), 3600s | 1800–10800s | Enough transitions, manageable size |
| CV folds | 10-fold | 5-fold | Fold 10 hit 0.985 F1 due to easy end-of-run segment — misleading |
| Model | RF, LGBM, XGBoost | XGBoost | Best Critical recall, sequential error correction |
| Class weights | Custom {Critical:3, Unstable:1.5, Stable:1} | `class_weight="balanced"` | Custom weights actually hurt performance |

## Known Issues / Gotchas

1. **OneDrive sync conflict:** If `joblib.dump()` throws `OSError: [Errno 5] Input/output error`, delete the old `.pkl` file first then re-run. OneDrive locks files during sync.

2. **GitHub 100MB limit:** All `.pkl` and `.csv` files are in `.gitignore`. Don't try to push them.

3. **Fold 10 anomaly:** With 10-fold CV, the last fold scores ~0.985 because the end of the simulation often has consecutive Stable states (trivially easy). Always use 5-fold.

4. **XGBoost label encoding:** XGBoost requires integer labels. `LabelEncoder` is used to encode/decode. Class order: `['Critical', 'Stable', 'Unstable']` → `[0, 1, 2]`.

5. **LightGBM verbose:** Always pass `verbose=-1` to suppress excessive output.
